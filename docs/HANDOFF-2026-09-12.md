## The one open problem to solve next

**Both-voices audio still does not win.** The latest call (10:26, v1.0.6) shipped
`app_voice_communication` (near side / employee only), not `app_voice_call`
(both parties). The VOICE_CALL retry added in v1.0.6 did not change the outcome.

**Most likely cause:** on this Xiaomi, `MediaRecorder.setAudioSource(VOICE_CALL)`
throws **`SecurityException`** (barred to our app), so `MediaRecorderStrategy`'s
new logic breaks out of the retry immediately (correct for a truly-barred source)
and falls to VOICE_COMMUNICATION. **This is unconfirmed** — MIUI suppresses our
Timber logs in logcat, so the exact exception was never seen.

**The blocker to progress is observability, and the fix is a diagnostic build:**
Timber logs do not appear in `adb logcat` on this MIUI phone (only system logs
do). So the next step is **NOT another guess** — it is to make the app record,
into a place we can read, exactly which audio source it tried and what each
threw. Concretely: add a tiny Room table (e.g. `capture_attempts(day, route,
result, error_class, at)`) that `MediaRecorderStrategy.tryStart` writes on every
attempt, then read it via
`adb -s 10.31.219.206:42749 shell run-as uz.bonvi.call cat .../databases/bonvicall.db`
(pull + sqlite as done all session). That turns "why did VOICE_CALL lose?" from a
guess into a fact — the discipline this whole codebase is built on.

Once the exact failure is known:
- If **SecurityException on VOICE_CALL**: it is genuinely barred for a normal
  app on this MIUI build. Then re-open the OEM-harvest path — but note MIUI ALSO
  bars the folder (see below), so the real question becomes *how does Moi Zvonki
  get both voices on this exact phone?* — which may mean it too only gets the
  near side, OR it uses a mechanism not yet found (recheck its `VoiceRecorder`
  and `MainService` smali in the scratchpad, and consider whether the user has
  actually confirmed Moi Zvonki's recordings contain the CUSTOMER's voice).
- If **IllegalState/timing**: the retry window or start-point needs tuning (we
  start at OFFHOOK = dialing; maybe the source needs a different
  OutputFormat/Encoder — Moi Zvonki's format switch is decoded in ASSUMPTIONS).

**Do not lose sight of what already works:** near-side audio DOES upload. The
employee's half of every answered call reaches the panel. If both-voices proves
impossible on a given handset, near-side + the customer's contact name is still a
working product — confirm with the CEO before spending days chasing VOICE_CALL.

### ⚠️ Second live problem, reported by the CEO at 10:31: audio upload is STUCK, not just slow

The 10:26 call's audio was still `pending_upload` **5+ minutes later** (checked
10:31), while Moi Zvonki showed the same call's audio "immediately". Earlier
calls uploaded in ~2 min, so this one looks **stuck**, not merely slow.

**Prime suspect:** the metadata queue is blocked behind a `validation_error`
row. The phone's `queued_calls` held `8086e498…` (a `call_log_recovery` payload)
and the earlier `3436e808…` failing with `lastErrorCode = validation_error`.
`CallUploader.drainOnce()` uploads a BATCH and audio follows metadata in the same
`CallUploadWorker` pass — if a poison metadata row keeps the batch returning
`retryLater`/failure, or `UploadPolicy` keeps re-queuing it, later calls (and
their audio) may wait behind it. **First action for the parallel session:** find
why those recovery calls are rejected `validation_error` by the server
(`POST /api/device/v1/calls` returns 200 but with a per-call `error.code` —
look at the server's calls-ingest validation and the exact recovery payload:
`{"...","capture_route":"none","audio_missing_reason":"app_not_running",
"source":"call_log_recovery","audio_expected":false,...}`). A `call_log_recovery`
row that can NEVER validate will park (good) — but confirm it parks rather than
blocking the queue, and confirm the new 10:26 audio is not waiting behind it.
Separately, the two structural delays (20 s `POST_CALL_DELAY_SECONDS` + the
WorkManager hop) still apply and are the "slow vs Moi Zvonki" gap once the stuck
case is cleared.

Reproduce/inspect: pull the phone DB (command below), read `queued_calls`
(`attempts`, `lastErrorCode`, `parkedAtEpochMillis`) and `audio_jobs`
(`attempts`, `lastErrorCode`); and `docker compose logs backend | grep
device/v1/calls` for the batch responses.

## What was fixed today (all on `main`, uncommitted working tree)

Nothing has been committed — the CEO has not asked to commit. All changes are in
the working tree.

1. **Subscription dropped on OFFHOOK → every outgoing call rejected
   `subscription_unknown`.** `PhoneStateReceiver` built `OffHook(callId)` without
   the number/subscription it had already resolved; `TelephonyCallbackSource`
   captured the enrolled SIM once at registration, when it was still null
   (service starts during enrolment, before E4 saves the SIM). Both fixed; the
   live source now refuses to register until a SIM is enrolled and re-registers
   on change, and it registered at `subId=1` on the wire after the fix. **This is
   what made calls start arriving at all.**
2. **`oemRecorderReachable()` was a hard-coded `false` stub** → OEM harvest never
   ran on any handset. Now a real probe (`storageProbe.hasAccess() &&`
   a real file present in `OemRecordingFolders.CANDIDATES`). Moot on this MIUI
   (folder barred) but correct for readable-folder handsets.
3. **OEM harvest scanned once, before the file existed.** MIUI flushes the file
   ~6–7 s after the call ends. `OemHarvestStrategy.stop()` now polls up to
   `RETRY_COUNT`(=10)×1 s. (Also moot here — folder barred — but correct.)
4. **`ContactNameResolver.resolve()` had NO caller (4th "finished-but-uncalled"
   on this project).** Wired into `ReconcileSweep`: the name is resolved FRESH
   per call (no cache), so a renamed contact shows its new name next call — the
   exact Moi Zvonki defect the product exists to fix. Server already treats
   `contact_name` as a `MUTABLE_FIELD`. `ProductionCallersTest` now guards it.
5. **VOICE_CALL never retried → near side only.** `MediaRecorderStrategy` now
   retries VOICE_CALL across a 15 s ring-to-answer window, waiting through
   `UNAVAILABLE` (still ringing) but breaking on `FORBIDDEN` (SecurityException).
   **This is the change that did NOT yet work — see the open problem.**
6. **Deep link never carried the server** (`server/src/modules/enrolment/landing.py`,
   `api/install.py`) → release builds could never be pointed at a server.
7. **`/data/releases` had no Docker volume** → published APKs vanished on
   `compose up`. Volume added + `test_compose_wiring.py` guards it.
8. **Backend `--reload` never reloaded on Windows** → edited code kept serving
   stale. `WATCHFILES_FORCE_POLLING=true` in compose.
9. **6 arch tests + 41 live tests assumed `/` path separators** → passed
   vacuously / failed on Windows. Fixed with `invariantSeparatorsPath` and a
   configurable live-server + admin password.
10. **`Instantiatable` lint false-positives** (Hilt+R8) downgraded in `lint.xml`
    with DEX evidence.

Full detail with the reasoning for each is in `docs/ASSUMPTIONS.md` (entries
dated 2026-09-12).
