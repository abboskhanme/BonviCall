## Settled by the client, 2026-09-04

These are decisions, not assumptions. Recorded here so there is one place to look.

- [2026-09-04] SIM fleet or real PBX? → **SIM fleet**: calls ride ordinary mobile SIMs, recorded on the handset, transferred to our server as soon as the internet returns → the client's own words ("telefonida yoziladi, internet yonishi bilan bizni serverga o'tkazishi kerak"); a PBX needs an operator contract and licensing wait, and the CallSentry trial proved the SIM model captures two-sided audio. PBX stays documented as the release-2 fallback.
- [2026-09-04] Who owns the phones and SIMs? → **The handsets are the employees' personal property; SIMs are usually company-issued, sometimes personal** → client's answer. This is the single most consequential fact in the project: it removes managed-device provisioning, makes battery and data budgets an adoption requirement, and means Bonvi cannot wipe, update or replace a device by fiat.
- [2026-09-04] What is the identity anchor — device or number? → **The registered phone number.** Admin enters the agent's number into the panel and capture/attribution happen against it → client's words: "eng muhimi ularning tel raqamini bizning bazaga kiritib qo'ysak shu bo'yicha record qilish". It is also the better key: it survives a phone change and matches BonviZvonki's last-9-digits convention.
- [2026-09-04] Is employee consent required before capture? → **No. Installation is mandatory and there is no consent gate** → client's words: "barchasi o'zimizning xodimlar, ruxsat kerakmas, majburiy o'rnatiladi".
- [2026-09-04] Are the legal opinion, the consent/notice paperwork and SMS in scope? → **No — all three removed entirely, out of scope (not deferred)** → client's words: "loyihadan yurist hulosasi, siyosiy hujjatlar, SMS degan qismlarni olib tashla, kerakmas, bu shunchaki kompaniya ichki loyihasi" — this is an internal company project. Withdrawn in place, ids retained for `docs/TASKS.md`: UC-28, N29, N30, B1.
- [2026-09-04] Where may the audio physically live, now that the jurisdiction analysis is out? → **An ordinary engineering choice — cost, latency, backup convenience** → the constraint that used to sit on N29 is gone; the only remaining rule is N20, that it stays on Bonvi-controlled storage and is never publicly reachable, which is an ownership requirement, not a legal one.
- [2026-09-04] Why 12 months' audio retention, now that it is not a compliance number? → **An operational and storage-cost decision** → 12 months keeps steady-state disk at ≈ 250 GB (N18) and covers a full year-on-year comparison; nothing else drives it.
- [2026-09-04] Was CallSentry trialled, and what happened? → **Yes; two-sided audio worked; no lost calls, no overnight service death, no battery or data complaints, nobody turned it off. The problem was installation and permissions** (developer mode and/or disabling Play Protect) → client's answer. This evidence, not my judgement, now orders REQUIREMENTS §4.2.

## From plan-analyst, 2026-09-04

### Scope

- [2026-09-04] Is AmoCRM (or any CRM) integration in scope? → No, out of release 1 → CallSentry's `AmoCrmApiService` + CRM-selection screen were scaffolding for a different customer; Bonvi's CRM-shaped needs live in BonviZvonki, and every CRM adapter is a second wire format to keep alive.
- [2026-09-04] Is SMS in scope in any form? → **No — removed entirely: no sending, receiving, logging, or SMS gateway dependency** → client's scope reduction. Number verification uses the callback route (agent dials a short server number, inbound caller ID confirms), which needs no third-party gateway.
- [2026-09-04] With SMS gone, how does the app prove it is on the registered number when the SIM's MSISDN is empty? → **The callback route is the only remaining fallback, so it must be verified per OEM *and* operator in M0** → inbound caller-ID presentation is decided by the network, not by us; a single untested operator that withholds CLI would block enrolment for everyone on it.
- [2026-09-04] Migrate existing MoyZvonki call history and audio? → No; BonviZvonki keeps its history, BonviCall starts empty → the user said "completely independent", and MoyZvonki only retains 30 days of audio anyway.
- [2026-09-04] Multi-tenant support? → No, single Bonvi instance → no second customer exists; multi-tenancy taxes every query forever.
- [2026-09-04] Are WhatsApp/Telegram/IMO voice calls captured? → No, cellular calls on registered numbers only → no Android API exposes them to a third-party app; the blind spot is documented in §5.6 and goes to the risk register.
- [2026-09-04] Release-1 sizing target? → Design for ~25 registered numbers and ~15,000 calls/month; must not architecturally block 100 → BonviZvonki's measured volume model (15 agents, 11,700 calls/month, 1,560 h audio/month) plus headroom. **The actual model mix is still unknown and is not assumed** (open item D1).

### Personal-device boundary (all new, all consequences of Q2)

- [2026-09-04] What happens to calls on a second, unregistered SIM in the same phone? → **Not recorded, not uploaded, not counted** — no metadata, no number, no audio → capturing an employee's private calls on their own handset is the fastest way to lose the fleet. Stated in the employee manual so the boundary is visible, not merely promised.
- [2026-09-04] What if the OS cannot tell which subscription a call belonged to? → Treat it as **unregistered** (fail-closed) and count it as `subscription_unknown` in the gap report → the OEM-inconsistent `PHONE_ACCOUNT_ID`/`SUBSCRIPTION_ID` columns mean guessing would risk uploading a private call; missing a work call is the lesser failure.
- [2026-09-04] May the app read the employee's contact book? → Only to resolve a name on-device, and a name is uploaded only for a captured registered-number call → on a personal phone the contact book is the employee's private social graph; the number is the identity anyway (BonviZvonki's L3 lesson).
- [2026-09-04] The OEM recorder records *all* calls including private ones — do we harvest from that shared folder? → Only files whose time window matches a captured registered-number call; everything else is ignored and never uploaded → the folder is shared between work and private calls, so the matching rule is the privacy boundary, not just a correctness detail.
- [2026-09-04] How does an agent know what is being captured? → The app permanently displays the recorded number on its main screen, and the agent can see their own calls → on hardware the employee owns this is the difference between a tool and surveillance, and it is the cheapest adoption lever available (N41).
- [2026-09-04] How is one installation per number enforced? → Server-side: verifying on a new phone binds the number to the new installation, sets the previous to `replaced` after accepting its queued records, and raises an admin notification → two live installations double-count calls; an unexpected re-binding is also what a stolen credential looks like.
- [2026-09-04] How is the agent↔number mapping stored? → **Time-boxed** (`valid_from` / `valid_to`), not a plain column → a company SIM reassigned from agent A to agent B must leave A's historical calls attributed to A. BonviZvonki's single `agents.phone` column cannot express this; do not copy it.
- [2026-09-04] Can Bonvi wipe or reclaim the device when someone leaves? → No; the product revokes the token, stops capture and deletes local audio, and shows `revoked_pending_confirmation` if the phone never reconnects → Bonvi does not own the hardware, and a product that implies a completed wipe would be lying.
- [2026-09-04] Who pays for the mobile data? → Applied default: Wi-Fi-first upload with a 1 GB/month cellular cap, and the cost is stated plainly in the employee manual → this keeps the cost negligible; surfaced to the client as business item B2 because an unexplained data charge on a personal phone is exactly what gets an app uninstalled.

### Installation and permissions (elevated by Q5)

- [2026-09-04] How is the app distributed and updated? → Signed APK from Bonvi's own server with an in-app updater; **not** Google Play and **not** MDM → Play policy prohibits call-recording apps and would reject the permission set; MDM requires device ownership Bonvi does not have.
- [2026-09-04] What happens when an employee does not update? → The server enforces a **minimum supported app version**: an old client is refused with an Uzbek "please update" message, but **its queued records are accepted first** → updates now depend on employee cooperation, so version drift is certain; refusing an old client must never destroy data.
- [2026-09-04] What if a step genuinely cannot be completed unaided (developer options, Play Protect exemption)? → The flow says so plainly, offers an admin-assisted path, and the panel marks the agent `needs_assisted_install` → a silently stalled enrolment looks identical to a working one, which is how a rollout quietly fails.
- [2026-09-04] Which `targetSdk` does the app use? → Left open as a live design decision for `plan-stack`/`plan-architect`, flagged as coupled to the recording route → CallSentry deliberately used `targetSdk 28` for legacy file access to `Recordings/Call`, which is a plausible cause of both the two-sided audio *and* the install friction; the two may be the same decision, and a low `targetSdk` has a deprecation clock.
- [2026-09-04] Is Android Enterprise work profile (BYOD) the answer to install friction? → **Not assumed, not recommended; scheduled as spike S2** → it is the standard route to permitting a corporate app on an employee-owned phone, but a work profile may be isolated from the personal dialer and therefore unable to see the calls at all, which would make it useless here.

### Roles and access

- [2026-09-04] Which role model? → Reuse BonviZvonki's `admin` / `manager` / `sales` / `viewer`, plus a machine `service` token → same company, same people; a second mental model would be a permanent tax.
- [2026-09-04] May a salesperson see their own calls and play their own audio in the panel? → Yes, own only, read-only → transparency is the stated mitigation for the biggest organisational risk (BonviZvonki `PLAN.md` R5) and matters more now that the app runs on their own phone.
- [2026-09-04] What does the `viewer` (sales-room TV) see? → Live board only; numbers masked to last 4 digits; no audio, no personal data → the screen hangs in a room visitors walk through.
- [2026-09-04] May anyone delete an individual call or its recording? → No; `DELETE` on a call returns 405 for every role including `admin`. Only the retention job deletes audio → otherwise the first bad call gets quietly removed and the dataset is worthless.
- [2026-09-04] Who may listen to recordings? → `admin` and `manager` with every playback audited; `sales` their own only; `viewer` never → proposed in Q3 and not disputed by the client.
- [2026-09-04] How is "wrong owner" reported to a `sales` user? → 404, not 403 → 403 confirms the record exists and leaks that another agent talked to that number.

### Data, formats and identity

- [2026-09-04] Wire timestamp format? → ISO-8601 with explicit UTC offset, plus the device's raw epoch millis and timezone in the same payload → ISO is self-describing and debuggable; the raw epoch lets the server compute clock skew instead of trusting the handset.
- [2026-09-04] Which timestamp orders the data? → Server receipt time is authoritative; device time is data, not truth → devices are wrong about time and users change it.
- [2026-09-04] Idempotency key for a call? → A client-generated UUID (`client_call_id`) created at call start, server upserts on it → CallSentry used `localId`, a per-install Room autoincrement that restarts at 1 after reinstall and collides across devices.
- [2026-09-04] Phone-number matching key? → Normalise to E.164, match on the **last 9 digits** → identical to BonviZvonki, where it was already solved; a second convention would guarantee mismatched clients.
- [2026-09-04] How is internal vs external decided? → Automatically from **all registered numbers** plus an admin-editable extra list accepting suffix rules (`*700`); < 6 digits = PBX extension = internal; an empty directory yields `unknown`, never `external` → BonviZvonki's hand-maintained setting starved (10 of 33 employees had a number) and a content-based classifier then mislabelled 82 of 98 calls.
- [2026-09-04] How is capture rate measured after go-live, with no adb on personal phones? → The app self-reports: it sweeps its own call log for the registered subscription every 6 hours and reports that count next to what it uploaded; the panel shows the delta → without this, N1 becomes unverifiable the day the acceptance window ends.

### Audio

- [2026-09-04] Audio format and bitrate? → Mono, 16 kHz, Opus ≤ 24 kbps (~10.8 MB/hour), transcoded on the device **before** upload → CallSentry's 44.1 kHz/128 kbps AAC is ~57.6 MB/hour ≈ 6 GB/agent/month of mobile data — unacceptable on a personal data plan; 16 kHz mono is the ASR-relevant band.
- [2026-09-04] Audio retention period? → 12 months, then automatic deletion; metadata and audit log indefinite → **an operational and storage-cost decision**: it holds steady-state disk at ≈ 200–250 GB and covers a full year-on-year comparison.
- [2026-09-04] Where does audio physically live? → One Bonvi-controlled object store; never a public or unauthenticated URL. **Which hosting, and where, is an ordinary engineering choice — cost, latency, backup convenience** → owning the audio is the entire point of the project (L1); beyond that, nothing constrains the location.
- [2026-09-04] Wi-Fi-only audio upload? → Wi-Fi preferred by default, but audio older than 24 h uploads over cellular anyway, subject to a per-device monthly cellular cap (default 1 GB) → a strict Wi-Fi-only rule means an agent who never sees Wi-Fi silently never delivers audio.
- [2026-09-04] Local queue capacity on a phone Bonvi does not own? → ≥ 30 days / ≥ 2,000 calls / **≥ 1 GB** audio; stop recording new audio and alert when the queue is full or the phone's free space drops below 1 GB; never delete captured audio; never drop metadata → 30 days of metadata is under 2 MB, so losing a call record is never the right trade — but filling an employee's personal storage is a fast route to uninstallation.

### Gaps in the SPEC that had to be filled

### The scheduler and the periodic jobs (T150, T151, T152), 2026-09-05

- [2026-09-05] Jobs hold a **PostgreSQL advisory lock**, not a row lock or a table flag → an advisory lock is released when its session dies, so a worker killed mid-job leaves nothing for a human to clear. A second worker that cannot take it **skips** rather than queues: a queued duplicate runs the job twice in a row, which is the thing being prevented, only later.
- [2026-09-05] **Every job is idempotent as well**, and that is not belt-and-braces → the lock does not protect against the case that actually happens, which is a worker restarting after a crash and running the same job again. Proven live: two workers with ticks 3 s apart both ran `command_timeout`, and that is harmless only because it is idempotent.
- [2026-09-05] `audio_retention` deletes the blob **first** and marks the row **second** → a crash between them leaves a row claiming a file that is gone, which the next run repairs because `delete` is idempotent. The other order leaves a file nobody deletes and nobody can find — the failure that running the job again cannot fix.
- [2026-09-05] `silence_detection` runs every five minutes **including at night**, and the working-hours arithmetic is what keeps it quiet → skipping nights in the cron expression instead would delay a real alert until well after Monday morning, and a holiday added to the settings would then need a redeploy to take effect. - [2026-09-05] The "three failures raise an alert" policy moved from `core/jobs.py` to `worker.py` as an injected `on_repeated_failure` → `core` must not import a module (§2), and the policy belongs to the composition root rather than to "run a function under a lock". ### Contract findings from the phone (2026-09-05)

- [2026-09-05] **Every 64-bit wire integer is declared without `format: int64`.** Pydantic's `int` is unbounded, so it reaches OpenAPI as a formatless `integer` and openapi-generator maps that to 32-bit `kotlin.Int`. `System.currentTimeMillis()` is ~1.77e12 against an `Int.MAX_VALUE` of 2.1e9; `free_storage_bytes` on a 128 GB handset is 1.28e11. Nine fields overflow: `device_epoch_ms` on `DeviceRedeemIn`/`DeviceCallIn`/`DeviceHeartbeatIn`, and the byte counters on `DeviceHeartbeatIn`/`DeviceEventDetailIn`. The server stores them all as BIGINT, so the **data model is right and only the wire schema is under-specified**. Stopgap: `android/scripts/widen_int64.py`, machine-applied and listed. `Int64WireContractTest` fails when a listed field gains the format — that is the signal to delete the entry, and the script with the last one. Server fix: `Int64 = Annotated[int, Field(json_schema_extra={"format": "int64"})]`.
- [2026-09-05] **`IssuedTokensOut` carries no `verification_method`.** SPEC §9.3 requires an attested binding to be "rendered differently from `number_verified` everywhere it appears", and E6 is the single most important place it appears — yet the response that completes verification does not say how the number was proven. `DeviceTokenPairOut` (the refresh response) does carry it. Worked around by reading `VerificationState.attested` from `DeviceVerificationStatusOut.state` and persisting the method locally; that is enough for E6 but means a client that only ever saw a refresh would be relying on the persisted copy. Adding the field to `IssuedTokensOut` would remove the inference.

### Capture pipeline decisions (T69, T68, T74, T67, T70)

- [2026-09-05] **Two call-detection sources, not one** → a manifest-registered `PHONE_STATE` receiver AND a `TelephonyCallback`/`PhoneStateListener` registered by the service. The receiver arrives when the process is not running, which is the case that matters: the first thing that happens after a reboot is often a call, and a phone that has not been opened since is still taking them. Both funnel into one `CallDetector`, so the rules exist once and are unit-testable.
- [2026-09-05] **The privacy boundary runs at DETECTION.** Guard 1 evaluates before any field is written; a call on an unregistered or unidentifiable SIM never enters the queue and leaves only a counter — no number, no time, no duration (N28). The recovery sweep applies the same filter to call-log rows, because the log holds the employee's private calls and a sweep that queued everything would upload what the live path correctly refused.
- [2026-09-05] `client_call_id` is **UUIDv5 written out by hand**, not `UUID.nameUUIDFromBytes` → that method is version 3 (MD5) and would silently disagree with the server's `uuid.uuid5`, uploading every recovered call a second time. `ClientCallIdTest` pins the output against a value produced by Python's `uuid.uuid5`, which is the only thing that makes N2's "duplicate rate must be 0" checkable from this side.
- [2026-09-05] The record is **not built when the call ends** → it is built by the sweep twenty seconds later, because the call-log row appears after the call and §3.10 rule 1 requires the id to come from the log's `DATE`. Building it early would mean a correction on every call rather than a right answer on most.
- [2026-09-05] `CallDetector` does not touch WorkManager; it calls an injected `CallEndedListener` → a class that touches WorkManager cannot be unit-tested, and the branches that would have lost their tests are the privacy-boundary ones. Found by a test failure, fixed by a seam.
- [2026-09-05] Four survival mechanisms, all of them (UC-05) → `START_STICKY`, `BOOT_COMPLETED`/`LOCKED_BOOT_COMPLETED`/`MY_PACKAGE_REPLACED`, an `AlarmManager` one-shot from `onTaskRemoved` (the only thing that runs after the process is gone when the user swipes the app away), and a 15-minute `WatchdogWorker` for "the OS stopped it and told nobody". The watchdog starts nothing before an installation exists — a notification on the phone of somebody mid-enrolment is the first thing they switch off.
- [2026-09-05] The upload worker retries rather than fails on a transient problem → a failed worker is never rerun, and the row it was carrying would sit in the queue until something else happened to schedule a drain. A one-shot on enqueue gives "within minutes"; the 15-minute periodic is the net for when the process died before scheduling it.
- [2026-09-05] A batch is confirmed **per call**, not per response → `POST /calls` accepts partially, and a call the server rejected must keep its row rather than vanish with the batch. A call the server did not mention at all also stays queued: dropping it would lose a call on a server bug.
- [2026-09-05] `CallRecordBuilder.reasonFor` guarantees an `audio_missing_reason` on every path (T75, N5) → an unanswered call is `not_expected` and a captured one `pending_upload`, both excluded from the gap report's denominator (SPEC §3.9), so a healthy fleet does not read as broken. With the OEM locators still `NoOp`, the honest fallback is `recording_route_unavailable` — a complete, correct record that names the right cause.
- [2026-09-05] `isReturnDefaultValues = true` for unit tests → the only Android call on the detector path is `SystemClock.elapsedRealtime()`, and returning 0 makes durations deterministic instead of dependent on wall-clock luck. Anything that genuinely needs Android behaviour belongs in an instrumented test.
- [2026-09-05] The call-log SIM-attribution column is named **only** in `capture/PrivacyBoundary.kt`, as `SIM_ATTRIBUTION_COLUMN` → `CallLogReader` projects it by reference and carries the value as opaque text; only the boundary interprets it. The constant deliberately does not echo the platform's name, so CONVENTIONS.md §8.1's grep check stays literally true and the name says what the column is for.

### Distribution and session decisions (T81, T79, T83, T80)

- [2026-09-05] The `int64` workaround is **deleted**. `build-backend` annotated the nine fields `format: int64`, `Int64WireContractTest` went red on the next run exactly as designed, `android/scripts/widen_int64.py` was removed and the generated DTOs now carry `kotlin.Long` unaided. The test stays with an empty list: its value now is catching the next one, and the last case in it fails on any new formatless `*_epoch_ms` or `*_bytes`.

- [2026-09-05] The debug LAN host is a **build-time substitution**, not a tracked address → `src/debug/network_security_config.template.xml` holds `__DEV_HOST__` and a Gradle task writes the substituted copy into `build/`. - [2026-09-05] `docs/ON-DEVICE-TESTING.md` written → everything so far is verified in a JVM and not one call has been captured on hardware. The doc is the shortest path from a laptop to a captured call, including the two tests that matter more than the happy path: a call on the OTHER SIM must produce nothing anywhere, and a call made in aeroplane mode must arrive late rather than never.
- [2026-09-05] **No state discards the queue** (`DeviceAuthState.holdsQueue` is `true` for all four, asserted by a test) → the natural implementation of "the token expired" clears local state, and what that clears is calls that happened and never reached the server. N25 exists because that failure is silent: the phone looks healthy and the panel simply has fewer calls than the handset made.
- [2026-09-05] Only a refused **refresh** produces `auth_expired`; a single 401 on a normal request does not → a 401 is a stale access token, which `TokenAuthenticator` refreshes and replays once. A network failure during refresh is explicitly NOT expiry: the session may be perfectly valid and the phone simply in a lift, and holding the queue for a reason that was not true is its own fault.
- [2026-09-05] `UPDATE_REQUIRED` keeps sending (T83/N34) → the server accepts a stale client's queued records and refuses it only once the backlog is empty. - [2026-09-05] `TokenAuthenticator` uses `runBlocking` → the second named exception to CONVENTIONS-CLIENT.md §8, for the same reason as `SessionStore`'s snapshot: OkHttp's `Authenticator` contract is synchronous, it runs on a background OkHttp thread and never on the main thread, and the alternative is no token refresh at all.
- [2026-09-05] Click-to-call discards commands older than **two minutes** and acknowledges them as stale (T80, UC-16) → the transport is not the risk (the hub measures 13 ms against a 5 000 ms bar); doze on MIUI/EMUI is. Acknowledged rather than dropped, so the panel can tell "arrived late" from "never arrived" — different faults, different fixes.

### Audio pipeline decisions (T73, T74, T84)

- [2026-09-05] Transcode happens **on the device, before upload** (N17) → mono 16 kHz Opus at 24 kbps, ~10.8 MB/hour, so the cellular budget and the storage budget are the same number. The prototype's 44.1 kHz / 128 kbps is roughly five times that and works out near **6 GB per agent per month of mobile data from a personal phone's plan** (R14, D6). Nobody would report that as the reason they uninstalled it.
- [2026-09-05] 16 kHz is a floor, not a target → N21 requires the audio to survive being fed to speech-to-text later **without a second lossy transcode**. 16 kHz is ASR's native input rate: resampling down to it is free, starting below it cannot be undone. Dropping to 12 or 16 kbps would save little and cost the thing the recording is for.
- [2026-09-05] Two encode targets, chosen by capability → Opus in Ogg where `MediaMuxer` supports it (API 29+), AAC-LC in MP4 otherwise. `MUXER_OUTPUT_OGG` arrived at API 29 and `legacy28` runs on 26–28 — the variant S1 says captures both voices, so it cannot be dropped. Both are 24 kbps mono 16 kHz, so the budget is identical and the fallback costs only being counted, which it is (`codec` and `capture_route` travel with every recording).
- [2026-09-05] **A transcode failure never loses the call** (UC-14) → every `TranscodeFailure` maps onto the closed `AudioMissingReason` enum, and a test asserts none of them maps to `pending_upload` or `not_expected`. Those two are excluded from the gap report's denominator, so a failure hidden behind either would make a broken fleet look healthy.
- [2026-09-05] **Wi-Fi first, cellular after 24 hours regardless** (T74, N14) → a recording that never uploads because the phone is never on Wi-Fi is a recording that does not exist, and the salesperson who is out all day is the one whose calls matter most. N14's 1 GB cap is the **ceiling, not the strategy**: at 24 kbps a heavy day is tens of megabytes, so the cap catches a fault rather than rationing normal use. Reaching it **holds** the recording; it never drops it.
- [2026-09-05] 409 `audio_not_attributable` is a **permanent per-item failure** → it is the privacy boundary at the far end: the server could not match the file to a registered-number call inside its window, refused it and wrote no bytes. The window does not reopen, so retrying spends the employee's data in a loop on a file the server has already decided is not the company's. Parked, reported, **and the local file deleted** — keeping a recording the server has refused is the one state worse than losing it.
- [2026-09-05] `AudioPipeline.deleteSourceIfOurs` → the app's own recordings are deleted after commit (N11); an **OEM-harvested file never is**, in any path including revocation. It is the employee's own recording in their own folder, opened read-only (CONVENTIONS.md §8.3), and deleting one would be a worse breach than never having captured it.
- [2026-09-05] Revocation (T84, UC-08) stops capture **first**, then deletes all local audio, and **keeps the metadata queue** → a phone interrupted after stopping capture but before deleting is recoverable; one that deleted and kept capturing is not. Audio is the sensitive artefact and metadata is the audit trail: deleting the first protects the employee, keeping the second preserves the record of what was captured before the revoke. 30 days of metadata is under 2 MB and carries no conversation.
- [2026-09-05] `AudioUpload` extracted as an interface → so `AudioPipeline`'s **deletion rules** are testable without a network. Those are the rules that matter most here, they are one-line mistakes, and neither is visible in production.

### Heartbeat, updater and manual (2026-09-05)

- [2026-09-05] The missing `app_version_code` was only half the bug: **nothing sent a heartbeat at all.** `DeviceCallsApi.heartbeat` existed with no caller, so a handset reported its version once at enrolment and never again — which is exactly why `unknown_version_count` was 5 of 5 on the live fleet. `service/Heartbeat.kt` now sends it, along with UC-17's device page: queue depth in records AND bytes, battery, the battery-optimisation exemption (re-reported every heartbeat, because an OEM update can revoke it silently and the first symptom is a phone that stops reporting overnight), storage, network type and whether the service is running.
- [2026-09-05] The version code is a **named contract field**, not a fourth header → `X-App-Version` and `X-App-Variant` already ride on the interceptor and adding another is one more thing to remember on the next endpoint. A named field renamed on the server is a compile error here. `HeartbeatContractTest` also asserts enrolment and heartbeat read the same `BuildConfig.VERSION_CODE`: if they diverge, raising the minimum strands a phone that has already updated.
- [2026-09-05] **An update never installs during a call, with no override** (T82) → installing an APK kills the process. A restart mid-upload is recoverable (the queue is on disk, the upload resumes, the upsert makes a replay harmless); a restart mid-capture is a lost call, and there is no recovery. - [2026-09-06] `Revocation.enforceIfRevoked()` runs from the upload worker and the heartbeat → the auth state flips to `revoked` inside a drain on a network thread, which is not where a deletion belongs. Idempotent and silent when there is nothing left, or a revoked phone still switched on would log the same warning every fifteen minutes for ever.
- [2026-09-06] The app opens on the **home screen** once `installation_id` and a **refresh token** exist → the refresh token is the only local fact that cannot be true on a half-finished install (the real pair is issued after verification). Every launch used to land on E1 and walk forward through the whole flow, including E5 — which would have started a fresh callback challenge on a phone verified weeks ago. A deep link carrying a code always wins, because that is UC-07's rebinding.
- [2026-09-06] A **revoked** installation does not resume past E1 and the home screen offers "Yangi kod kiritish" → the id is still on the phone, so the resume rule would have skipped the agent past the one screen they need. A successful redeem clears the old auth state, or a re-enrolled handset would stay locally `revoked` and capture nothing for no visible reason.
- [2026-09-06] `StubScreen` was deleted with the last stub it rendered → a screen no route can reach is the same defect as a string nobody renders, and `UzbekCatalogueTest` caught the orphaned string within a minute of the home screen becoming real.
- [2026-09-06] `ProductionCallersTest` asks the question `docs/STATUS.md` says to ask — **who calls this in production?** — of eleven capabilities the fleet depends on. Verified by deleting two callers and watching it fail. Four finished-and-uncalled components had already shipped on this project; this is the mechanism, not another reminder.
- [2026-09-06] **The capture path had no caller either.** `CaptureRouterFactory` and `AudioPipeline` were built, tested and never constructed, so every call was queued with `capture_route = none` and no recording — on a product whose purpose is the recording. `CaptureCoordinator` now runs one router per call id (R5: call waiting is two calls, and one "current recording" would splice them).
- [2026-09-06] Recording starts at **answer**, not at the first ring → an unanswered call has no conversation to record and ships as `not_expected`, which is what keeps the gap report's denominator honest; and a recorder started against a ringtone competes with the dialler for the microphone.
- [2026-09-06] The capture outcome is written onto the `pending_calls` row, not held in memory → the service is killed between a call ending and its audio being queued on most of this fleet, and in memory that is a recording of a call that happened, lost. Room migration **1 → 2**, additive only.
- [2026-09-06] Audio is queued in its own table (`audio_jobs`) and drained **after** the metadata → the server accepts a recording only against a call it already holds, and `client_call_id` does not exist until the sweep derives it from the call log twenty seconds later. A field on the queue row would not work: that row is deleted the moment the server confirms it, while a twenty-minute recording takes several passes.
- [2026-09-06] `CallCapture` is a seam so `CallDetector`'s privacy-boundary branches stay testable without a phone — those branches decide whether a private call is recorded, and they are the reason the package is arranged this way. The fake in `CallDetectorTest` asserts the property that matters: a rejected call never reaches `prepare`, so a recording is impossible for it.
- [2026-09-06] The OEM harvest window's upper bound is still the provisional one the detector's guard uses (`Long.MAX_VALUE`) → the decision is made while the call is ringing and the end time is not known then. Inert today because `NoOpOemRecordingLocator` returns null, and **T71b must bound the window itself**; the comment saying so is in `CaptureCoordinator.prepare`.
- [2026-09-06] `RoomMigrationTest` compares the migration SQL against the schema Room exported rather than against the entity source → Room is what refuses to open the database, and with `fallbackToDestructiveMigration` forbidden, a drifted migration is a phone that cannot open the queue it is holding. Verified by deleting one `ADD COLUMN` and watching it fail.

### Why the handset went silent, and what CallSentry did (2026-09-06)

- [2026-09-06] **`CaptureService` held no wake lock.** CallSentry acquires a `PARTIAL_WAKE_LOCK` for the service's whole lifetime (`CtiForegroundService.onCreate`, `setReferenceCounted(false)`, released in `onDestroy`) and stays alive on these handsets; BonviCall declared `WAKE_LOCK` in the manifest at T22 and never used it. The first real install went silent 19 minutes after the screen went off — socket dead at 19:07, the 15-minute heartbeat never ran. Ported as-is, with the same guard: an OEM that refuses the lock is a phone that sleeps through its calls, which the gap report shows; it is not a reason to refuse to run.
- [2026-09-06] **`phoneCall` foreground-service type adopted, reversing the "DO NOT ADD" decision.** The old reasoning was right about the rule and wrong about the app: API 34+ accepts the default-dialer role, **MANAGE_OWN_CALLS**, or device ownership, and MANAGE_OWN_CALLS is a *normal* permission — install-time, no dialog, nothing an agent sees. CallSentry qualifies exactly that way. What it buys: exemption from Android 15's six-hour `dataSync` budget, and permission to be restarted from the background, which is what the watchdog does after an OEM kill.
- [2026-09-06] The type is **chosen at runtime, best first** — `phoneCall|microphone`, then `microphone|dataSync`, then untyped — because the manifest cannot express "try this, then that" and a type the app does not qualify for throws. `CaptureService.activeType` records what the OS accepted and it is reported as the `foreground_service` capability's detail, so the fleet answers the question with data instead of an argument. CallSentry does the same fallback one level down (`phoneCall|microphone` → `phoneCall`).
- [2026-09-06] **Opening the app restores capture** (`MainActivity.onStart`), and a successful heartbeat restarts the service if it is not running. A foreground service started from a visible Activity is always allowed, including API 31+, while every other mechanism (START_STICKY, boot, watchdog) is deferred while the OS holds the app down. Nothing used the one signal that always works.
- [2026-09-06] `ManifestPermissionsTest` now pins the inverse rule: `phoneCall` may be declared **only** where MANAGE_OWN_CALLS and FOREGROUND_SERVICE_PHONE_CALL are, and the service must be seen to try-and-fall-back rather than assume. A reversed decision keeps a test; it does not lose one.

### The enrolment dead end, and the step budget (2026-09-09)

- [2026-09-09] **No handset on this fleet had any route to `active`, so the app was an install that captured nothing.** Route 1 needs the SIM to report its own MSISDN, which Uzbek SIMs do not; route 2 needs an always-on callback receiver, which the client has never provided; admin attestation existed and **could not reach the phone**, because the real token pair is minted at verification and there was no device-facing endpoint to collect it. Every enrolment therefore reached E5, was told "contact the admin", and stopped — with the installation left `pending`, which the server refuses every call from. Two additions close it: `POST /enrolment/verify/self` (route 3) and `GET /enrolment/status`.
- [2026-09-09] **Route 3, `self_declared`, is the fourth binding and the weakest.** It claims only that whoever held the single-use code an admin issued *for one specific number* typed it into this handset; no line is proven. Recorded as its own `verification_method`, its own `funnel_stage` and its own audit action, so §9.3's rule holds — the identity anchor degrades visibly or not at all. The panel renders it `warn` with "Raqam tasdiqlanmagan", and attestation stays **offered** on such an installation rather than treated as already bound, which turns self-declaration into a queue an admin works through instead of a hole. Governed by `enrolment.allow_self_declared`, default **true**: the alternative default is a fleet that cannot enrol.
- [2026-09-09] `GET /enrolment/status` hands over the pair whenever the installation is active, whatever activated it → this is what makes panel attestation reach the phone at all. E5 polls it every five seconds while `awaitingAttestation`, so a screen that said "contact the admin" completes itself the moment they act rather than leaving the agent watching a sentence that stopped being true.
- [2026-09-09] `PROVISIONAL_TOKEN_SECONDS` was the literal `900` and the token is minted for `DEVICE_ACCESS_TOKEN_HOURS` — the app was told fifteen minutes and given twelve hours. Now derived from the same constant. A client that believed the number would have discarded a working credential and stranded itself on E5.
- [2026-09-09] **E2 asks for every runtime permission in one request.** It walked nine capabilities one card at a time — nine taps before anything happened, on the step of an unaided install where people already stop. Six of the nine are ordinary runtime permissions and Android shows those dialogs back to back from one `RequestMultiplePermissions`; the other three are settings screens and keep their own buttons, only while they are not already satisfied. **What did not change is the part that matters**: every capability is still exercised afterwards and a row goes green only when its check passes, never because a dialog was dismissed.
- [2026-09-09] E5 offers "Keyinroq tasdiqlash" even when the callback route IS available → a proven binding is worth more than a declared one, so the challenge is still shown first, but a screen whose only exit is "dial this number and wait five minutes" is where an unaided install ends.
- [2026-09-09] **`CaptureService.start()` can no longer throw.** From API 31 a background `startForegroundService` is refused unless the app is exempt, and the exemption relied on is the battery-optimisation one an agent is allowed to decline (UC-14). `PhoneStateReceiver` called it unguarded, so a handset whose agent skipped that step would have **crashed on every incoming call** — indistinguishable from a broken app. The guarantee now lives in `start()` itself rather than as a try/catch per call site, one of which would eventually be forgotten. The per-call-site guard in `EnrolmentModule` was removed as redundant.
- [2026-09-09] The foreground-service candidate list gained a **`dataSync`-only** last resort. From API 34 the `microphone` type requires RECORD_AUDIO to be granted; without a microphone-free candidate both earlier candidates throw, the untyped fallback inherits the manifest's types and throws for the same reason, and the service does not start at all — so a phone that should have logged calls without audio logged nothing and reported nothing.
- [2026-09-09] `NumberVerification.isBound(state)` replaced the same rule written out in two places, which had already drifted: the repository knew about `self_declared` and the readiness check did not, so a handset holding a real token pair still rendered as unenrolled and refused to start capturing.
- [2026-09-09] The service-level "revoked" guard in `complete_self_declared_verification` was deleted before it shipped → the principal resolver already refuses both revoked states with 401 before any route sees the request, so it was a branch no request could take. An unreachable guard is worse than none: it reads as the place the rule lives, so the day the real one moves nobody looks there. The behaviour is pinned at the wire instead.

### The real handset finally recorded — and why nothing arrived (2026-09-12)

Ilyoshon's Xiaomi 13 Lite (HyperOS/MIUI V140, Android 13, `2210129SG`), read live over wireless ADB. The handset's own recorder had written every call into `MIUI/sound_recorder/call_rec` (51 files, the folder first in `OemRecordingFolders.CANDIDATES`), Moi Zvonki showed the same recordings, and BonviCall shipped nothing. The app's own Room database named the cause without ambiguity: `discard_counters` held one row, `subscription_unknown = 6`. Six outgoing calls, six fail-closed rejections at Guard 1, on a phone that had recorded all six.

- [2026-09-12] **`PhoneStateReceiver` dropped the subscription (and the number) on OFFHOOK.** The `when` built `Ringing(callId, number, subscriptionId)` but `OffHook(callId)` — both fields discarded. An OUTGOING call is reported `IDLE → OFFHOOK → IDLE` with no RINGING, so OFFHOOK is its only edge; every outgoing call therefore reached `SubscriptionRule` with `subscriptionId = null` → `SUBSCRIPTION_UNKNOWN`. The data was in hand (`boundary.subscriptionIdFrom(intent)` resolved it to 1, matching the enrolled SIM and the call log) and thrown away one line later. `TelephonyCallbackSource` was given this exact fix on 2026-09-11; the receiver sibling was missed — STATUS.md's "go looking for its siblings" rule, written down and not followed.
- [2026-09-12] **The live source captured the enrolled subscription once, at registration, when it was still null.** `CaptureService` starts DURING enrolment, before E4 saves the SIM, so `enrolledSubscription()` returned null; the registration fell through to the unscoped `TelephonyManager` and the callback was handed `subscriptionId = null` for the life of the process. `register()` returns early while `registered != null`, so it was never re-read — and a process restart during enrolment is exactly what does not happen. Confirmed on the wire: `dumpsys telephony.registry` showed our listener at `subId=2147483647` (default), identical to Moi Zvonki's own registration. Fixed by **refusing to register until a SIM is enrolled** and re-registering when it changes (`registeredSubscriptionId`): an unscoped stream is never labelled with the enrolled id, because on a dual-SIM handset that would attribute the employee's private calls to the work SIM and upload them. After the fix and an app restart the listener re-registered at `subId=1`.
- [2026-09-12] **Both `subscriptionIdFromCallLogAccount` (recovery from the call log's own `PHONE_ACCOUNT_ID`) and the fixes above are needed together.** The live path now attributes an outgoing call correctly; the sweep already reads the call log's subscription column, so a call the live path still misses is recovered — as metadata, `app_not_running`, no audio. The audio path itself was never in question: the folder, the files, the window rule and the all-files permission were all verified present.
- [2026-09-12] **Moi Zvonki is the same architecture, confirmed from the installed app** (`com.cloudoftechnologies.mycalls`): `targetSdk`-legacy behaviour, a plain `PhoneStateListener` at the default subscription, no per-SIM scoping. Where it works, the handset's own recorder writes the file and the app harvests it — there is no capture magic to copy. The difference was never the recorder; it was two places where our subscription id was dropped between the OS and Guard 1.

### Why the OEM harvest never won, and reading Moi Zvonki to be sure (2026-09-12)

After the subscription fixes, the first live-captured call finally reached the server with audio — but as `app_voice_communication` (near side only), not `oem_harvest` (both voices). The customer's half of a sales call is the entire point, so this mattered.

- [2026-09-12] **The OEM harvest scanned once, at call-end, before the file existed.** The handset's own recorder flushes its file a few seconds AFTER the call ends: measured +6 s and +7 s on Ilyoshon's Xiaomi 13 Lite (`stat` on `MIUI/sound_recorder/call_rec/*.mp3` vs the call-log end time). `RawPathOemRecordingLocator` did a single scan and returned null, so `MediaRecorderStrategy`'s live mic recording (VOICE_COMMUNICATION) won every time. The `RETRY_COUNT`/`RETRY_INTERVAL_MS` constants existed *for exactly this* and nothing used them. `OemHarvestStrategy.stop()` now polls up to `RETRY_COUNT` times (10 × 1 s), which does not widen the boundary — the window is fixed by the call, so a later scan can only match this call's own file. Verified by two tests (a late file is found after N scans; give-up after RETRY_COUNT with no trailing sleep).
- [2026-09-12] **Why VOICE_CALL (the both-sides mic source) lost too, and why we didn't chase it.** `MediaRecorderStrategy` tries `VOICE_CALL` first, but `capture.start()` fires at OFFHOOK — which on an OUTGOING call is dialing, before the remote answers and before the voice path exists — so `VOICE_CALL` throws and we fall through to `VOICE_COMMUNICATION` in one shot, with no retry. Read off the **installed Moi Zvonki APK** (`com.cloudoftechnologies.mycalls`, "Save My Call", targetSdk 28) to confirm the mechanism: its `VoiceRecorder.a(I)I` maps recording-mode 0 → `AudioSource.VOICE_CALL` (4) for SDK ≥ 23, and its caller retries start on failure (`SystemClock.sleep(100)` loop). So Moi Zvonki gets both sides by *retrying VOICE_CALL until the call connects*. We could adopt that, but on this fleet the OEM recorder is on and writes a cleaner both-sides file than any mic source can — so fixing the harvest timing is the lower-risk win and is the app's own preferred route. The VOICE_CALL retry is the fallback improvement for handsets whose own recorder is off (noted, not yet built).
- [2026-09-12] Moi Zvonki confirmed to have **no capture mechanism we lack**: same targetSdk-28 legacy model, `PhoneStateListener` at the default subscription (`subId=2147483647`, identical to our pre-fix state), MediaRecorder with VOICE_CALL, and OEM-file harvest. It is not scoped per-SIM because it is a consumer recorder with no privacy boundary — it records every call. Our two bugs were the subscription being dropped between the OS and Guard 1; the recorder was never the difference.

### The contact name was never sent, and why audio is slower than Moi Zvonki (2026-09-12)

- [2026-09-12] **`ContactNameResolver.resolve()` had no caller in production — the FOURTH instance of this failure shape on this project.** The resolver was correct and careful (single `PhoneLookup` row, no cache, takes a `Decision.Capture` as proof), `CallRecord` had no `contactName` field, `CallRecordBuilder` never set one, and `ReconcileSweep.toWire()` never put one on the wire. So every call shipped `contact_name = null` and the panel showed a raw number. This is worse than the Moi Zvonki defect the product was built to fix: theirs showed a STALE name, ours showed NO name. Wired end to end — the sweep now reconstructs the capture proof (it already had to, for the boundary) and resolves the name at record-build time. **Resolution is per call and uncached by construction**, so renaming a contact to `K00213 Diljahon aka` shows the new name on the next call. The server already treated `contact_name` as a `MUTABLE_FIELD`, so a re-ingest of the same `client_call_id` updates it — that half was ready and waiting. `ProductionCallersTest` now carries the row that would have caught it.
- [2026-09-12] **Why our audio reaches the server minutes after Moi Zvonki's.** Measured against the competitor's own code: its `MainService` has no post-call wait at all — it uploads with an id it generates itself. Ours waits, by design, in three places that add up: `ReconcileWorker.POST_CALL_DELAY_SECONDS` (20 s) because `client_call_id` is derived from the call log's DATE (§3.10 rule 1) and the platform writes that row after the call; the new OEM harvest poll (up to 10 s) because HyperOS flushes its recording ~7 s late; and a WorkManager hop between `ReconcileWorker` and `CallUploadWorker`. The phone is not being throttled — `dumpsys jobscheduler` shows our jobs `Standby bucket: EXEMPTED`, `readyNotRestrictedInBg: true`, and the app is in the doze whitelist, so none of this is an OEM battery manager. The 20 s is the biggest single lever and the only one that can be cut without losing something; cutting it needs the measured call-log-row latency on this fleet, not a guess.

### The OEM folder is barred on MIUI — both voices come from VOICE_CALL instead (2026-09-12)

- [2026-09-12] **MIUI bars other apps from `MIUI/sound_recorder/call_rec`, even with MANAGE_EXTERNAL_STORAGE granted.** `adb shell run-as uz.bonvi.call ls /sdcard/MIUI/sound_recorder/call_rec/` returns `Permission denied` while `appops get uz.bonvi.call MANAGE_EXTERNAL_STORAGE` is `allow`. The folder is `media_rw`-group, `rw-rw----`, and MIUI does not remap it for a third-party holder of all-files access. So the OEM harvest — the app's documented preferred route — cannot read the file on this fleet's phones, and `oemRecorderReachable()` (now a real probe) correctly returns false, skipping the strategy. The harvest-poll fix from earlier today is still correct for handsets where the folder IS readable; it is simply moot here.
- [2026-09-12] **Moi Zvonki does not harvest the folder either — it records VOICE_CALL itself.** Confirmed from the installed APK: it holds no MANAGE_EXTERNAL_STORAGE (so on Android 13 it cannot raw-read the MIUI folder any more than we can), and its `VoiceRecorder.a(I)I` selects `AudioSource.VOICE_CALL` (4) for SDK ≥ 23, with the caller retrying start on failure (`SystemClock.sleep(100)` loop). VOICE_CALL carries both parties and is permitted to a targetSdk-28 app on these Xiaomis; the recorder is not the difference between the two products.
- [2026-09-12] **Our VOICE_CALL lost because we start at dialing and never retried.** `capture.start()` fires at the OFFHOOK edge, which on an outgoing call is dialing — VOICE_CALL is refused until the line CONNECTS, so a single attempt threw and `MediaRecorderStrategy` settled for VOICE_COMMUNICATION (near side) for the whole call. It now retries VOICE_CALL across a 15 s ring-to-answer window (`CONNECT_RETRIES`), and **only where the platform reports it UNAVAILABLE, never FORBIDDEN** — a `SecurityException` (a handset that bars the source to apps) breaks out immediately so the near-side fallback is not delayed, while an `IllegalStateException` (still ringing) is waited through. `stopRequested` cuts the wait the instant the call ends. Runs on the live call-state path, which carries no broadcast budget. Three tests, including the retry-then-connect and the forbidden-no-retry cases.

### Second session, same phone: the two handoff problems had different causes (2026-09-12, evening)

Everything below was measured on Ilyoshon's Xiaomi 13 Lite over wireless ADB, with
Moi Zvonki 1.1.66 installed beside BonviCall 1.0.6 (code 7). The handoff's two open
problems — *both voices never win* and *audio upload is stuck* — were both real, and
both had a cause other than the one the handoff suspected. The previous section's
three claims are corrected here, with the measurement that overturns each.

- [2026-09-12] **The app's own microphone recording is SILENT for the whole call on
  Android 10+, so "near-side audio uploads" was never true.** `dumpsys audio` keeps the
  recording history: every one of our `VOICE_COMMUNICATION` sessions is flagged
  `silenced` from start until telecom sets `MODE_NORMAL`, and flips to `not silenced`
  only after hang-up (e.g. 15:27:00 start silenced → 15:27:32 not silenced → 15:27:41
  stop). ffmpeg on the pulled file of the 15:26 call: 0–31.7 s digital silence
  (`RMS_level=-inf`), then six seconds of the employee's voice AFTER the call — the ten
  seconds the mic keeps running while the OEM poll waits. This is the platform's
  concurrent-capture policy (an ordinary app is silenced during a phone call; only the
  dialer, accessibility services on `VOICE_RECOGNITION`, and holders of
  `CAPTURE_AUDIO_OUTPUT` are not), not an OEM quirk. Consequences: `app_voice_communication`
  and `app_mic` recordings on any Android 10+ handset are silence, `VOICE_CALL` is refused
  to every third-party app by `AudioPolicyService` (it needs `CAPTURE_AUDIO_OUTPUT`, a
  signature|privileged permission) and surfaces as a non-Security exception, so the
  15 s retry window added in 1.0.6 only delays a silent fallback. The "near-side +
  contact name is still a product" fallback in the handoff does not exist on this fleet.
  The handset's own recorder is the ONLY source of a conversation.
- [2026-09-12] **Moi Zvonki never opens the microphone on this phone — it harvests the
  MIUI folder, by plain `File` path.** Two independent measurements: `appops get
  com.cloudoftechnologies.mycalls` shows no RECORD_AUDIO usage at all across today's
  calls (ours shows every one), and the `dumpsys audio` record history holds no session
  for its uid. Its decompiled `SystemHelper` (jadx, `C.java`) maps `xiaomi` →
  `MIUI/sound_recorder/call_rec`; its `needsSaf()` returns false below targetSdk 30, so
  with targetSdk 28 it reads the folder directly, and `dumpsys activity permissions`
  confirms it holds no persisted document-tree grant. The previous claim "MIUI bars the
  folder even with MANAGE_EXTERNAL_STORAGE" rested on `adb shell run-as ... ls`, which
  runs in the `runas_app` SELinux domain with the shell's storage view — not the app's.
  Moi Zvonki reading the same folder with the same legacy-storage grant is the proof the
  app's own process can. The `storage_access` capability now reports the file COUNT of
  every OEM folder it can list, so this is measured by the app itself from now on.
- [2026-09-12] **Why our harvest matched nothing: the window overflowed.** `CallDetector`
  evaluates a ringing call with `endedAtEpochMillis = Long.MAX_VALUE`; `decide()` copies it
  into `Decision.Capture` unchanged; `OemRecordingMatch.windowFor` added the 120 s
  post-buffer to it, which wraps negative, so the range was empty and every file failed
  `in window`. The strategy DID run — the mic recording stopped 9–10 s after each call,
  which is the ten polls — and reported `attribution_failed` ten times per call on a
  handset with 51 clean files in the folder. `CaptureCoordinator.prepare`'s own KDoc had
  warned "T71b must bound that window itself". Fixed twice over: `OemHarvestStrategy.stop()`
  bounds the end to the stop time (the tighter, honest boundary — a later call's file can
  never fall inside it), and `windowFor` saturates instead of overflowing so no other
  caller can reintroduce the silent-empty-range failure. A match is also taken only once
  its size holds still across two consecutive scans, because the OEM writer grows the
  file during the call. Four new tests, including one that pins `endedAt = MAX_VALUE`.
- [2026-09-12] **Why audio was "stuck": the transcoder hung, and each new pass cancelled
  the last.** `audio_jobs` held five rows, all `attempts = 0` — no pass ever finished OR
  failed a job. `MediaCodecAudioTranscoder.signalEncoderEnd` handed the encoder its
  end-of-stream marker with a single `dequeueInputBuffer` and dropped it when that
  returned -1 (the encoder's input queue was full, because the loop drained one output
  per decoded frame and one AAC frame becomes three Opus frames); the encoder then never
  signalled its own end and `while (!sawEncoderEnd)` spun. `feedEncoder` likewise dropped
  the remainder of a buffer when the queue was full. Logcat showed `CallUploadWorker ...
  was cancelled` every ~5 min (`ExistingWorkPolicy.REPLACE` from the sweep's re-enqueue),
  the cancellation was never observed by the blocking loop, and `top -H` showed four
  `MediaCodec_loop` and two `OggWriter` threads: two zombie transcodes holding codecs.
  Fixed: the encoder is drained fully on every iteration and whenever an input slot is
  missing; the end marker is retried, never dropped; a loop with no buffer movement for
  30 s fails THAT job (`capture_returned_silence`) so the queue moves on; the pump runs
  under `runInterruptible` and checks for interruption, so a cancelled worker releases its
  codecs; and `enqueueNow` is `APPEND_OR_REPLACE`, so a running pass completes. The 09:07
  upload that did succeed earlier shows the hang was timing-dependent, not universal.
- [2026-09-12] **The two `validation_error` rows were unanswered outgoing calls sent as
  `answered`.** The server's log names the constraint: `ck_calls_answered_has_duration`.
  On an outgoing call the platform reports OFFHOOK at dialling and the live path takes
  that as the answer, so a call nobody picked up (call-log duration 0) shipped
  `disposition=answered, duration_sec=0` and was refused; its recording of the ring tone
  sat in `audio_jobs` behind the parked metadata. `ReconcileRule.answeredAt` now lets the
  call log decide: duration 0 means nobody answered, the call ships `no_answer` /
  `not_expected`, and the app's own dial-tone recording is deleted (an OEM file never is).
  The parked rows were not blocking the queue — the drain skips parked rows — so the
  handoff's "poison row" hypothesis was not the stuck cause.
- [2026-09-12] **The recovery sweep re-sent every call in its two-day lookback on every
  run, and rewrote live calls as `app_not_running`.** Section 2 of `ReconcileSweep` skipped
  only rows matched to calls still in `pending`; a live call already enqueued and removed
  from `pending` was "never seen" on the next sweep and re-queued as `call_log_recovery`
  with `audio_missing_reason = app_not_running`. Both fields are `MUTABLE_FIELDS`
  server-side, so the correction was applied: on the panel the 14:09, 14:37 and 15:04
  calls — all live-captured, all with an audio job waiting — read `app_not_running` /
  `call_log_recovery`. The same re-sends cost data every 30 minutes and were what kept
  re-enqueuing (and cancelling) the upload pass. A recovery WATERMARK (`SessionStore`,
  `recovery_watermark_epoch_ms`) now records the newest call-log row the sweep has
  handled; rows at or below it are never handled again. It advances only over rows that
  were matched or recovered, so a row Guard 1 refuses is re-examined and a call still in
  flight cannot be skipped (its row does not exist yet). Overlapping calls (call waiting)
  are the one case a row can be passed over; it is accepted and noted here.
- [2026-09-12] **Timber lines never reach `adb logcat` on this MIUI build**, which is why
  a day of diagnosis ran on `dumpsys`. Debug builds now also plant a `FileLogTree`
  (behind `RedactingTree`, rotated at 1 MB) writing `files/logs/bonvicall.log`, readable
  with `run-as`. Never in a release build (N26).
- [2026-09-12] `OemFolderStorageAccessProbe` kept its own five-entry folder list from
  before `OemRecordingFolders` existed, without any Xiaomi path, so on an API 26–29
  Xiaomi it would have answered "no readable recordings folder". One list now.
- [2026-09-12] Not changed, recorded for the next decision: (a) the `VOICE_CALL` retry in
  `MediaRecorderStrategy` costs 15 s per call for nothing on Android 10+ and the mic
  fallback there produces silence; the honest next step is to detect
  `AudioRecordingConfiguration.isClientSilenced()` and report `capture_returned_silence`
  instead of uploading silence, and to skip the mic route entirely where the OEM route
  produced a file; (b) on handsets with NO manufacturer recorder, an Android 10+ third-party
  app cannot record a call at all without an accessibility-service trick — that is a
  fleet-policy decision for the CEO, not a code change; (c) `POST_CALL_DELAY_SECONDS`
  (20 s) stays until the call-log row latency is measured here — today's rows appeared
  within 2 s of hang-up.

### The same phone, one hour later: three more causes under the first ones (2026-09-12, evening, continued)

- [2026-09-12] **`RedactingTree` dropped every log line the app ever wrote — on every
  handset, not only MIUI.** It was `class RedactingTree(delegate: Timber.Tree)` whose
  `log` called `delegate.log(priority, tag, redact(message), t)`. Kotlin cannot reach a
  protected member through a receiver of the base type, so that call bound to Timber's
  PUBLIC `log(priority, message, vararg args)` overload with the tag in the message slot;
  the tag is null at that point and `prepareLog` swallows an empty message with no
  throwable. Found by the first JVM test that planted a tree and read the line back
  (`FileLogTreeTest`): it failed with the file never created. The handoff's "MIUI
  suppresses our Timber logs" was this bug. `RedactingTree` is now a `DebugTree`
  subclass calling `super.log` (the protected hook on its own instance, which Kotlin
  allows); `FileLogTree` redacts for itself. Verified on the handset: `files/logs/
  bonvicall.log` filled from the next start, and the same lines now appear in logcat.
- [2026-09-12] **The live call-state source never registered after a process restart.**
  `CaptureService.onCreate` was its only caller and runs before `SessionStore` has read
  its DataStore, so `enrolledSubscription()` answered null, the source declined
  ("no enrolled SIM yet") and nothing ever called it again — the KDoc's "retried on
  every heartbeat and E6" named callers that did not exist. `dumpsys telephony.registry`
  after the 16:02 update: zero registrations for the app. The 15:23 install had won the
  race by luck. The service now also collects `SessionStore.simSubscriptionId` and
  re-registers with the emitted id (`register(scope, subscriptionId)`); `register` and
  `unregister` are `@Synchronized` because two callers now exist. Verified: `subId=1
  phoneId=0 events=[6]` within five seconds of the next restart.
- [2026-09-12] **The manifest receiver could never attribute a call on this handset.**
  `dumpsys activity broadcasts` shows every `PHONE_STATE` broadcast MIUI sent today with
  extras `{state, incoming_number}` and nothing else — no subscription, no slot — and no
  `SUBSCRIPTION_PHONE_STATE` broadcast at all. So every receiver-delivered edge reached
  Guard 1 as unknown and was discarded (`subscription_unknown = 22` by 16:10); with the
  live source down, that was the CEO's 16:08 call, lost live and recovered later without
  audio. Three changes: the receiver also listens for `android.intent.action.
  SUBSCRIPTION_PHONE_STATE` (the per-subscription form, which carries the id where a ROM
  sends it); an edge with no subscription is neither handled nor counted (the labelled
  sibling or the live source owns the call — counting it was the "cosmetic double count"
  that hid the loss); and `SubscriptionPrivacyBoundary.subscriptionIdFrom` resolves an
  unlabelled edge to the ONE active subscription when the OS lists exactly one — a fact
  from the OS's own list, not a preference, and a dual-SIM handset still gets null.
- [2026-09-12] **A recovered call now harvests the handset's own recording.** The OEM
  route is post-hoc by nature; a call the live path missed has passed the same Guard 1
  (filtered by the call log's attribution column) so the same `Decision.Capture` can be
  built from its log row and the same locator asked. Before this, every recovered call was
  `app_not_running` on a phone whose recorder had written the conversation. Bounded by
  the log row's own window, never writes or deletes (CONVENTIONS.md §8.3).
- [2026-09-12] **Two upload passes ran at once and raced on one work file.** The one-shot
  and the periodic `CallUploadWorker` are separate unique works; the moment the transcoder
  stopped hanging, two sessions opened for one call a second apart and the first commit
  was refused `checksum_mismatch` (a permanent refusal that discards the job). `AudioDrain`
  now runs one pass at a time behind a `Mutex`.

### The first both-voices recording, and the four things it exposed (2026-09-12, 16:27–16:40)

The CEO's 16:27 call was the first one captured end to end on this fleet: the
app's log shows `OEM harvest: 58 candidate file(s) in range, one matched`, the
server holds it as `live_capture`, `has_audio = t`, `capture_route =
oem_file_harvest`. On the way it exposed four more defects, each fixed the same
hour.

- [2026-09-12] **The recording arrived three times too long.** The handset's
  recorder writes 48 kHz mono MP3; the transcoder decoded it and handed the
  samples to an encoder configured for 16 kHz mono with no conversion between,
  so a 36 s call became a 1 min 48 s file at a third of the pitch (ffprobe on
  both files). The file's own header had promised "decode → resample → encode"
  and the middle step did not exist; the app's own recordings never showed it
  because `MediaRecorderAudioRecorder` records at the encoder's rate exactly.
  `PcmResampler` (linear interpolation, channel averaging, the last frame of
  each buffer carried into the next) is built from the decoder's actual output
  format; four JVM tests pin the arithmetic, including 48 kHz → 16 kHz across
  uneven buffer boundaries. The 16:27 recording on the server is the stretched
  one and stays as evidence; the next call is the verification.
- [2026-09-12] **`APPEND_OR_REPLACE` was a regression and is reverted.** With
  one audio job answering 409 `call_not_found` on every pass (the ring-tone job
  of the unanswered 15:04 call, whose metadata the server will never accept),
  `CallUploadWorker` returned `Result.retry()` and sat in exponential backoff
  (attempt 6: sixteen minutes; the periodic worker at attempt 8: over two
  hours). APPEND chained every new one-shot BEHIND that backoff — WorkManager's
  database showed three `bonvicall.upload.now` rows `BLOCKED` — so the freshly
  queued 16:27 call waited while Moi Zvonki showed it in seconds. `REPLACE` is
  back: a cancelled pass now unwinds cleanly (the transcoder fix), loses nothing
  that was already uploaded, and "a call was queued" means "drain now". Two
  further changes so a poisoned job cannot do this again: `call_not_found` is
  reported through `Interrupted.code` and is NOT counted as unfinished (no
  retry backoff — only the metadata drain can change it), and after twelve such
  passes the job is given up with a log line; the app's own file is deleted, an
  OEM file never is. A forced `cmd jobscheduler run` does not bypass
  WorkManager's own backoff, for the record.
- [2026-09-12] **One call, two sessions.** Once the receiver could attribute an
  edge (the single-active-SIM rule), the live callback (`live-<n>`) and the
  receiver (`sub-<id>`) each opened a session for the same call: two recorders
  started, the OEM file was located twice, both reconciled to the same log row
  and the queue deduplicated the record. `CallDetector.begin` now treats an
  edge for a SIM that already has a call in flight as that call's edge from the
  other source, bounded to three hours so a session whose end edge was lost
  cannot shadow the SIM. Two tests.
- [2026-09-12] `dumpsys activity broadcasts` confirmed why the receiver was
  ever unattributed here: MIUI's `PHONE_STATE` extras are `{state,
  incoming_number}` only, and no `SUBSCRIPTION_PHONE_STATE` broadcast is sent
  at all. On this handset the single-active-SIM rule is the whole receiver path.
- [2026-09-12] Left as is, noted: `CallSessionManager` reports "Resuming 7 call
  session(s)" on every start — `ENDED` rows are not deleted because `ENDED` is
  not marked terminal in `CallStateMachine`. Cosmetic; it should be looked at
  before the fleet grows a year of rows.
- [2026-09-12] **Verified end to end at 16:43.** One session (`live-…` only —
  the same-SIM rule held), `OEM harvest: 59 candidate file(s), one matched`,
  server row `live_capture` / `has_audio = t`, `call_audio.capture_route =
  oem_file_harvest`, `duration_ms = 35560` for a 35 s call (the resampler),

- [2026-09-12] **The CEO's question "is the problem in the APK?" — yes, all of
  it.** Every defect found today lived in the app; the server rejected only
